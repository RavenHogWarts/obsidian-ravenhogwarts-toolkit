# 工具详解：Plugin Order（插件加载顺序）

> 工具 id：`plugin-order` ｜ 版本：1.2.0 ｜ 设计记录：[`dev/plugin-order-design.md`](../dev/plugin-order-design.md)

## 这个工具做什么

把**一个或多个**指定插件 id（按配置顺序）保持在 `community-plugins.json` 数组最前，
从而控制其最先加载。只调顺序、**绝不增删条目**；未启用/未安装的配置 id 自动忽略。

典型场景：某插件启动期一次成型的 UI（如 Ribbon 图标）引用了晚注册的资源而显示空白——
让它（或它的依赖方）最先加载即可解决。

## 机制原理

- 社区插件按 `community-plugins.json` 的**数组顺序**串行加载（Obsidian 无优先级/依赖 API）。
  该文件是仅含**启用中**插件 id 的裸数组。
- 每次启用/禁用插件 Obsidian 都会重写该数组——被重新启用的插件追加到**末尾**。
- 本工具在四个时机把配置 id 上浮回最前：**OTK onload**（启动）、**配置变更**
  （设置页保存后自动触发）、**插件启停/增删**（监听 `app.plugins` 的 `changed` 事件，静默；
  该事件先于 Obsidian 写盘触发，故先等 `community-plugins.json` 落盘后再重排）、
  **手动命令 / 设置页「立即应用」**。
- 顺序只在启动读取时生效：**修改对当前会话无效，下次启动生效**。

## 已安装插件缓存

设置页每次应用时会把**全部已安装插件**（无论是否启用）缓存到本工具的
`data.installedPlugins`。数据源 = 运行时 `app.plugins.manifests`（类型由
`@obsidian-typings` 增强 `App.plugins: Plugins`；Obsidian 启动时已解析全部已安装插件的
manifest，含未启用，直接读取零 I/O）。一律走内置 API、不做目录扫描；保留运行时形状校验，
异常构建下 `manifests` 缺失即返回空缓存。

缓存用于配置的**三态反馈**——设置页编辑器以徽标明示每个配置 id 的状态：

| 状态 | 含义 | 处理 |
| --- | --- | --- |
| 优先加载 | 已启用（在数组中） | 按配置顺序上浮 |
| 已安装未启用 | 装了但没开 | 本次忽略；启用后下次 enforce 生效 |
| 未安装 | 没装 / 已卸载 / 笔误 | 忽略 |

例：配置 `(A, B, C)` 而 B 未启用 → 文件中 A、C 上浮到最前，B 不动（编辑器徽标标为「已安装未启用」）。

## 安全规则

1. 配置目录经 `vault.configDir` 动态获取，不硬编码 `.obsidian`；
2. 文件结构异常（非 `string[]`、含非字符串项、含重复 id、JSON 解析失败）→ 不动文件；
3. 仅重排已存在条目，**绝不增删**（把禁用插件写回会导致幽灵启用状态）；
4. 结果与原数组一致时不写文件（幂等，无谓 IO 与 mtime 抖动）；
5. 所有读-算-写经 promise 链串行化，不与下一次 enforce 交错。

## 与 custom-icons「始终最先加载本插件」共存

obsidian-custom-icons 的实验性开关会把自己的插件（`custom-sidebar-icons`）提到数组最前。
**两侧同时启用时，本工具的优先列表必须包含 `custom-sidebar-icons`**，否则每次启动
双方互相改序、后执行者胜，文件顺序来回翻转（抖动）。列表包含它时两者目标一致，无冲突。

## FAQ

**改了配置为什么当前会话不生效？**
数组顺序只在 Obsidian 启动读取时生效。保存配置或执行命令后，重启 Obsidian 生效。

**会话内重新启用某个优先插件后顺序乱了？**
不必手动处理了。Obsidian 会把它追加到数组末尾，但本工具监听 `app.plugins` 的
`changed` 事件，**静默**把它重排回最前——下次启动即按配置顺序加载。
（`changed` 先于 Obsidian 写盘触发，故工具会先等 `community-plugins.json` 落盘、
再读取并重排，避免读到旧文件；当前会话已加载的顺序需重启才会变化，这是 Obsidian 机制使然。）
「立即应用插件排序」命令作为兜底保留。

**卸载本工具后顺序会变吗？**
不会。重排是对文件的一次性写入，不驻留任何后台进程。
